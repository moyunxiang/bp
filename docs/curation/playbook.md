# 局内打法表的写法规范

适用文件：`data/curated/playbook.json`（打法条目）和 `data/curated/archetypes.json` 里每个体系的 `play`、`against`。

这两份内容回答的是“这一局怎么打”：我方怎么打、对面的突破口在哪、要防什么、出装怎么针对。它们是**通用战术说明**，和体系定义里的 `winCondition` 同一性质，不是数据结论，界面上也是这样标注的。

## 一条打法条目的结构

```json
{
  "id": "open_reveal",
  "section": "opening",
  "title": "用视野技能找隐身英雄",
  "text": "{a}的视野技能留给{e}：对方靠隐身接近，被照出来之后就失去先手。",
  "when": [
    { "side": "ally", "as": "a", "cond": { "tags": ["reveal"] } },
    { "side": "enemy", "as": "e", "cond": { "tags": ["stealth"] } }
  ],
  "basis": "隐身单位被显形后失去先手优势。"
}
```

- `section`：`plan` 我方怎么打（只能用我方条件）；`opening` 对面的突破口；`danger` 要防的点；`build` 出装与召唤师技能。后三类必须至少有一句针对对面的条件。
- `when`：每一句是“某一方满足条件的英雄数在 [min, max] 之间”。条件用 `cond`（与规则表相同的写法：官方职业、已核实标签、`none`）或 `feature`（与阵容分析一致的特征：`frontline` `hardCC` `aoeCC` `engage` `protect` `waveClear` `physical` `magic` `mixed`）。
  - 只写 `min`（默认1）表示“有”。
  - 写了 `max` 表示“没有/不超过”。这类判断只在该方选满5人、且用到标签时全队档案都可用的情况下才成立，所以不能给它起名（`as`）。
- `text`：用 `{名字}` 引用命中的英雄，用 `{items}` 引用装备。同一个名字在一句话里尽量只出现一两次，后面用“对方”“它”指代。
- `items`：装备原文关键词。界面会列出官方装备说明里含有这个关键词的装备，所以点名的装备始终有原文可查。
- `basis`：这条说法依据的通用机制，一句话。

## 能写什么，不能写什么

能写：

- 能从触发条件直接推出的打法。条件是“对面有隐身英雄”，就只能写和隐身有关的应对。
- 站位、技能交给谁、先后顺序、什么时候接团这类操作层面的建议。
- 标签定义本身包含的事实（标签定义见 `data/curated/tags.json`）。

不能写：

- 具体数值、射程、伤害比较、冷却时间（标签里没有这些信息）。
- 标签推不出来的英雄特性。例如条件只判断了“有位移”，就不能写“它的位移可以穿墙”。
- 强度判断和胜负断言：“稳赢”“必输”“碾压”“版本强势”“胜率”“T0”等。
- “对面一定会……”这种绝对说法。用“会”“容易”“考虑”。
- 没有原文依据的装备。需要点名装备时必须用 `items` 关键词。

写完后自查：把触发条件里的英雄换成任何一个同样满足条件的英雄，这句话还成立吗？不成立就说明写进了条件之外的东西。

## 体系的 `play` 和 `against`

- `play` 分四句：`early` 前期、`mid` 中期、`fight` 团战、`avoid` 不要做什么。
- `against`：对面是这个体系时怎么打。
- 只依据体系的判定条件和 `weakTo` 来写，不涉及具体英雄。

## 修改后

```bash
npm run build:data && npm run validate && npm test
```

校验会检查：条件里的标签和特征存在、文字里引用的名字都定义过、装备关键词能在官方装备说明里找到、没有禁用表述。
